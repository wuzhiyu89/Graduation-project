### 3.2 判断：`cfg_t` 5 → 2 是**可行的**，省 7,932 B

三条依据（都需要在改动前用测试验证，不能只信注释）：

**（a）`chk` 可以删 —— 把"反序列化后逐字段比"改成"JSON 字节比"**
`config_store_save()` 现在的流程是：序列化到 `s_json_wr` → 写 Flash → 回读到 `s_json_rd` → 反序列化到 `chk` → 与入参比较。
`cfg_serialize()` 对同一份 `cfg_t` 的输出是**确定性**的（无时间戳、无指针），所以直接 `memcmp(s_json_rd, s_json_wr, n)` 就能判定，`chk` 整块可以不要。
**验证方法**：改完后跑 `test_cfg` 全套（含"写入非法配置必须拒绝"、"掉电只写一半时回落旧配置"这些用例）。

**（b）`s_merge_tmp` 可以删 —— 让 `config_store_merge_sections()` 直接操作入参**
`config_parse.c:786` 是 `memcpy(&s_merge_tmp, c, sizeof(*c))`，之后所有解析都写在 `s_merge_tmp` 上。而调用方 `cloud_cmd_cfg.c:118` **已经**先 `memcpy(&cloud_cfg_staging_buf, config_store_get(), ...)` 再传进来 —— 也就是说入参本来就是一份可写的副本，`s_merge_tmp` 是第二份。
**必须先核对的**：`config_parse.c` 的 `merge_sections` 还有哪些调用方（`cloud_cmd_devices.c:200` 也调它）。逐个确认"传进来的指针是可写副本，且失败后调用方不依赖它保持原值"。只要有一个调用方直接传了 `config_store_get()`（只读指针），就不能删。

**（c）`s_cfg_reset_tmp` 与 `cloud_cfg_staging_buf` 共用**
`cloud_cmd_cfg.c:321` 的注释已经写"与恢复出厂共用一块 scratch"，但实际是两个独立变量。合并前要确认 `cfg.reset` 和 `cfg.set` **不会同时持有**（单线程轮询命令，理论上不会，但要把两条调用栈都画一遍）。

### 3.3 现状：6 块 ≥6 KB 的 JSON 缓冲（合计 37,249 B ≈ 36.4 KB）

| 符号 | 位置 | 大小 | 用途 | 能否去掉 |
|---|---|---:|---|---|
| `s_json_wr` | `config_store.c:129` | 6,144 | 保存载荷 | ❌ |
| `s_json_rd` | `config_store.c:130` | 6,144 | 从 Flash 读回的原文 | ⚠️ 与 (a) 一起改后可考虑 |
| `s_json_crc` | `config_serialize.c:20` | 6,144 | CRC 复算专用 | ✅ **能**（见下） |
| `s_data_buf` | `cloud_proto.c:46` | 6,208 | 云命令信封里的 `data` 段 | ❌ |
| `jsonbuf` | `app_downlink.c:57` | 6,209 | 收到的下行报文原文 | ⚠️ |
| `resp` | `app_downlink.c:63` | 6,400 | 命令应答缓冲 | ⚠️ |

**能立刻确认可去的只有 `s_json_crc`**：它是"算 CRC 时用的临时缓冲"，而 `s_json_wr` 里已经是同一份 JSON —— CRC 直接在 `s_json_wr` 上算即可（注意算完不能改内容，实际上也不会改）。

**`jsonbuf` / `resp` / `s_data_buf` 三合一先别动**。理由：它们可能在同一调用栈里**同时有效**（`cloud_proto_handle(jsonbuf)` → 抽出 `data` 到 `s_data_buf` → 生成应答到 `resp`，此时 `jsonbuf` 可能还要被回读用于回显 `msgId`）。要做必须先实测重叠：
> 在 `cloud_proto_handle()` 入口打印三个缓冲的地址与生命周期节点，或用 `#if` 加一段"若地址重叠则触发断言"的临时代码，跑一遍 `cfg.query`（最大应答）+ `cfg.set`（最大请求）。

### 3.6 ★实施结果（2026-11-12 收尾补记，下一轮直接看这里）

任务二已按 **A′ + B′** 执行完毕，C 档未做。上面 3.2 / 3.3 有三条判断经实际代码复核后**不成立**，已按代码事实修正：

| 原判断 | 复核结论 |
|---|---|
| (b) 删 `s_merge_tmp`，`merge_sections` 原地操作入参 | ❌ **没删，本轮保留**。`config_parse.c:878~905` 是【逐域事务】：每个域都从当前 `*c` 重新拷一份 `s_merge_tmp` → 只应用该域 → validate → 成功才 `memcpy` 回 `*c`，失败丢弃并继续下一域。原地改入参会让失败域污染配置。要省这 2,644 B 得另做"按域字节快照回滚" |
| 3.3 "CRC 直接在 `s_json_wr` 上算即可" | ❌ `config_store_calc_crc(c)` 的入参是**结构体**，必须重新序列化一次才能拿 CRC；`s_json_wr` 里那份是 save 的载荷，不是入参。正确顺序是：先让 save 的回读不再复算 CRC，再把 `calc_crc` 实现从 `config_serialize.c` 移到 `config_store.c` 借用 `s_json_wr` |
| 3.1 `s_cfg_reset_tmp` "恢复出厂 / `cfg.reset` 的 scratch" | ⚠️ 当时**已经**被 `cfg.query`(321) 和 `sys.factory_reset`(397~425) 共用（23 行注释写明了），只是还没并进 `cloud_cfg_staging_buf`；文件头 5~6 行"三条命令共用 staging"反而是不准确的 |

**实际改动**

- 删 `chk`(2,644 B)：新增 `cfg_bank_verify_written()` = 头部 `magic`/`hdr_crc` 校验 + `version`/`updated_at`/`crc32`/`json_len`/`seq`/`rsv` 逐项比 + JSON 原文 `memcmp`。被 `load` 共用的 `cfg_bank_read()` 一行未改，**开机校验强度不变**
- 合并 `s_cfg_reset_tmp`(2,644 B)：`cfg.query` / `sys.factory_reset` 统一用 `cloud_cfg_staging_buf`
- 删 `s_json_crc`(6,144 B)：`config_store_calc_crc()` 搬到 `config_store.c` 借 `s_json_wr`；`s_json_wr` 的独占约束写在 `config_store.c` 文件头与 `config_store.h` 的 API 注释里（**禁止在 `config_store_save()` 调用栈内复算 CRC**）
- 新增 `test_cfg` 一条断言：save 后 A/B 两区逐字节一致 —— 防"A 区载荷被覆盖、但 load 回退 B 让测试照样全绿"

**实测**：RAM 169,858 → **158,426 B**（−11,432 B ≈ 11.2 KB，余 37.3 KB）；Flash 172,648 → 172,784 B（+136 B，新增校验函数）；Keil 0 Error / 0 Warning；13 套件全绿。`s_merge_tmp` 仍在 `CDC.map` 的 ≥1 KB 符号里，是**预期**而非漏改；因此 A+B 实际省下 11.4 KB，不是 3.4 表预估的 14 KB。

### 4.1 规范（用户 2026-11-12 定稿）

- **管理面新增独立前缀** `rt/mgmt/{gwId}/`，只需要 4 条：

## 5. 执行顺序与理由


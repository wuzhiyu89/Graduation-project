## 一、设备 type 取值约定（§一）—— 已实现

| type | 设备类型 | 网关行为 |
|---|---|---|
| 1 | 水位传感器 | `dev.bind` 带 1 = 按液位传感器绑定 |
| 3 | 声光一体机 | `dev.bind` 带 3 = 按联动设备绑定 |

- **配对/绑定流程的 type 不再使用 null**：网关侧配对事件（`dev.pair`）固定上报 `type: 1` 或 `type: 3`，不会出现 null；`dev.bind` 缺 `type` 直接回 `1001`；
- `type` 传其它值（如 `2`）回 `1001`；

## 二、`telemetry.report` 的 `effective.levelCm` 改最大值（§二）—— 已实现

- `effective.levelCm` 现为**各在线（已启用且未超时）传感器水位的最大值**，单位 cm，保留一位小数；
- 与 `effective.status` / `effective.gear` **同一判定源**（阈值判定本来就是取最大），三者天然一致，不会再出现"`levelCm` 说 Normal、`gear` 进了 Warning"的自相矛盾；
- **`sensors[]` 逐台的 `levelCm` / `rawMm` 原样保留**，每台各自的时间戳不变，贵方可照旧保存每台各自的值；
- 生效范围：网关在线后第一条遥测起即为新口径，无需配置变更。

> 说明：记录里 7.1 与 0 的平均值 3.5 那个例子，现在会报 `7.1`（= 最大值）。

## 三、manual 模式与传感器离线策略（§三）—— 已实现

| 项 | 结论 |
|---|---|
| manual 模式下 `sensorOfflinePolicy` | **完全不生效**：既不做 keep/alarm/off 的档位覆盖，也不在 manual 结束后"补做"一次，避免把云端刚手动设定的档位顶掉 |
| `manualTimeoutSeconds` 手动控制时可改 | **支持**：`rule.set` 带 `mode:manual` 与 `manualTimeoutSeconds` 即覆盖本次窗口；`dev.ctrl` 每次手动控制也会重置窗口计时 |
| 退出 manual | 恢复到 auto 后，下一拍按**当时**实际状态重新判定； |

## 四、管理/业务双 MQTT 常驻连接 —— 评估通过，建议走双连接

### 4.1 资源评估结论

| 项目 |  | 结论 |
|---|---|---|
| MCU RAM |  增加连接状态、管理面 4 个 topic、URC 分流与独立收发缓冲 | 余量充足 |
| 模组 MQTT 连接数 | 支持 `connect_id` 双路连接 | 可行 |
| 模组 MQTT 报文缓存 | 两条连接分别缓存 | 充足，但**不做离线消息堆积**，超限即丢弃 |
| AT 通道 | 单串口 115200 | 可行 |
| 短信下行 | 不支持 | 不支持 |
| 流量增量 | 每连接心跳（60 s）约 0.17 MB/月 | 第 2 路 + 周期报到 ≈ **+0.4 MB/月** |  150 MB/月余量足够 |

### 4.2 结论

**走双连接（管理面 + 业务面各一条常驻连接）**

### 4.3 配套约定

1. **连接 × 命令域白名单**：管理类命令仅管理连接受理，业务命令仅业务连接受理，越权按现有错误码显式拒绝，不静默忽略；
2. **主题分面**：管理面 `rt/mgmt/{gwId}/...`，业务面 `rt/gw/{gwId}/...`（沿用 §9.4 的 4 个 topic）；
3. **降级路径保留**：任一连接连不上时，另一条不受影响；业务面主备 IP 都失败 → 回退厂家管理 IP；
4. **凭据独立**：两套账号互不可知，业务凭据由管理平台下发并支持远程轮换。

## 六、周期性回厂家平台报到 —— 开启，建议默认周期 1 小时

| 项 | 约定 |
|---|---|
| 是否开启 | **开启** |
| 周期 | **3600 秒（1 小时）**，可配置（60 s ~ 24 h） |
| 报文 | `rt/mgmt/{gwId}/checkin`，轻量：固件版本、配置版本、在线子设备数、信号强度、运行时长；**不含业务数据** |
| 时机 | 周期 + **随机抖动（±5 分钟）** + 事件触发补报 |
| 流量 | 约 **0.75 MB/月**，相对 150 MB/月 可忽略 |

**补充**：配置变更生效后、OTA 完成后、连续 3 次连不上业务平台时，立即厂家平台补报一次，不等下一个周期。

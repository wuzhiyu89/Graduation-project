# 缓存分层规划：RAM 放什么、外挂 Flash 放什么

> 版本 v1.1 / 2026-11-11
> 起因：`event_cache` / `telemetry_cache` 现在把同一条数据**先放 RAM、满了再搬到 Flash**，
> 属于"双份存储"。用户判断这条路不对，要求先定分层再改代码。
>
> **状态：已按方案 A 实施完毕（S1~S3）。** 本文保留原有的推演过程，
> 但 §4 中"规划期假想"的部分已按实际实现订正（见 §5 状态列、§6 拍板结论）。

---

## 1. 现状盘点：数据到底在哪儿

### 1.1 RAM 里的东西

| 数据 | 模块 | 大小 | 掉电要不要留 | 谁在用 |
|---|---|---|---|---|
| 传感器最后值快照 | `last_value`（`data_cache_up_push` 是唯一漏斗） | 5 槽 × ~44 B ≈ 220 B | **不用**（下一帧就回来） | 遥测 JSON、`sen.query`、告警判定、变化量基准 |
| 待下发指令队列 | `data_cache`（down） | 16 × ~236 B ≈ 3.8 KB | **不用**（秒级重试） | LoRa 下发 |
| 待确认遥测暂存 | `app_uplink` 的 `s_tel.pend` | < 200 B | **不用** | 转进补报缓存 |
| 离线逐条上报 | `telemetry_cache` | 128 × 32 B = **4.0 KB** | **要** | 补报 `telemetry.report` |
| 离线事件 | `event_cache` | 256 × 28 B = **7.0 KB** | **要** | 补报 `event.report` |
| 配置 9 个域 | `config_store` | ~3 KB × 2 份 | 要（在**内部** Flash） | 全部业务 |

> 缓存类合计约 **11 KB**（整机 ZI ≈ 174 KB）。

### 1.2 外挂 Flash（8 MB）里真正接上的

| 区 | 大小 | 现在有没有人写 |
|---|---|---|
| META | 64 KB | ✅ 环指针（只用 2 个扇区 = 8 KB） |
| EVENT | 2 MB | ✅ 只在 RAM 满时溢出 |
| TELEM | 3 MB | ✅ 只在 RAM 满时溢出 |
| FW_FACTORY | 1 MB | ✅ 产线写、运行期只读 |
| SPARE | 320 KB | 只给 `#flash selftest` 用 |
| **CFG** | 64 KB | ❌ **没有任何代码引用** |
| **LOG** | 1 MB | ❌ **没有任何代码引用** |
| **OTA** | 512 KB | ❌ **没有任何代码引用** |
| **FACTORY** | 64 KB | ❌ **没有任何代码引用** |

也就是说：**4.6 MB 是纸面分区，另有 2 MB 的 EVENT/3 MB 的 TELEM 只在"RAM 溢出"时才被写。**

## 2. 为什么"既放 RAM 又放 Flash"不好

不是审美问题，是可量化的五个代价：

| # | 代价 | 具体表现 |
|---|---|---|
| 1 | **掉电窗口大** | 数据先在 RAM 攒着，满了才落 Flash。真正需要掉电保护的恰恰是"刚开始断网、RAM 还没满"的这一段 —— 此时一条都没进 Flash，重启全丢 |
| 2 | **补报顺序倒挂** | Flash 存的是**最旧**的一段（RAM 满时推出去的），RAM 是**最新**的一段；补报从 RAM 头开始 ⇒ 先发新、后发旧。实测 200 条：发出去是 `73..200` 再 `1..72`，最后落到平台的是 2 小时前的值 |
| 3 | **两份指针要同步** | RAM 有 `g_rd/g_wr/g_cnt`，Flash 有 `head/tail`，META 还有第三份（节流落盘）。任何一处 `reset` 漏了另一边，就会出现"换绑后把上一位用户的数据补报给新账号" |
| 4 | **写入时机最差** | 平时不写，一旦写就是"批量倒灌"，正好撞上扇区擦除（45 ms 典型 / 400 ms 最大），主循环在最忙的时候被打断 |
| 5 | **RAM 白占** | Flash 能存 4.9 万条，RAM 还为同样的数据留 11 KB，且只覆盖 128/256 条 |

## 3. 三个候选方案

| | A. Flash 就是队列（单写） | B. RAM 为主 + Flash 只做掉电快照 | C. 现状（RAM 热 + Flash 冷尾） |
|---|---|---|---|
| 写入点 | 每条待补报记录**直接写 Flash**，RAM 不留副本 | 只写 RAM；每 30 s 或每 32 条整块快照进 Flash | RAM 满了才搬 Flash |
| 容量 | 4.9 万条（TELEM 3 MB） | 128 / 256 条 | 4.9 万条但只用 128 条热 |
| 掉电丢多少 | 最多 1 条（META 节流窗口内可能重复 1 条） | 最多一个快照周期 | 最多 RAM 里那一整批（128/256 条） |
| 顺序 | 天然按写入顺序 | 天然顺序 | **倒挂** |
| 运行期 Flash 写 | 有节奏地写（= 记录产生速率） | 周期性大块写 | 突发批量写 |
| 复杂度 | 中（要一层后端抽象） | 低 | 高（两份指针 + 恢复对账） |
| 适合 | 断网要存几百小时 | 只要能扛重启 | — |

**结论：选 A。** 理由：这个产品真正要保护的只有"补报队列"，它必须掉电保留、量可能很大，正是 Flash 该干的活；而 RAM 里其他东西（快照、下发队列）都是秒级时效，掉电丢了下一拍就回来，根本不该进 Flash。

B 的唯一优势是"运行期零 Flash 写"，代价是容量被 RAM 锁死（128 条 ≈ 2.7 小时），和"断网存几十天"的目标冲突。

> **★2026-11-11：用户已拍板按 A 实施，S1~S3 全部完成（见 §5）。**
> 实施后 `telemetry_cache` / `event_cache` 的 RAM 环形已删除（合计省 11 KB RAM），
> 补报顺序由"倒挂"变为严格按 `ts` 递增。

## 4. 推荐架构：单一写入点 + 可插拔后端

### 4.1 归属表（定稿口径）

| 数据 | 归属 | 理由 |
|---|---|---|
| 传感器最后值快照 | **RAM** | 秒级时效；掉电后靠下一帧重建 |
| 待下发指令队列 | **RAM** | 秒级重试；失败由平台重下发 |
| 待确认遥测暂存 | **RAM** | 同上 |
| **待补报上行队列（遥测 / 事件）** | **外挂 Flash（唯一副本）** | 唯一"必须掉电保留 + 量大"的数据 |
| 环指针 / 统计 | 外挂 Flash META | |
| 配置 | 内部 Flash | 已有 `param_save`，不动 |
| 出厂固件 | 外挂 Flash `FW_FACTORY` | 只读基线 |
| 运行日志 | 外挂 Flash `LOG` | **二期**，本期不接 |
| `CFG` / `OTA` / `FACTORY` 区 | 暂不接，保留 | 内部 Flash 已够；OTA 有 A/B 槽 |

### 4.2 实际实现：直接调存储层，不做后端抽象

规划期设想的是"一层接口 + Flash/RAM 双后端"，**实际没这么做**——因为 Q3 已明确
"没有老板子，不考虑老版本兼容"，RAM 后端没有存在意义，多一层抽象只是多一处分叉。

实际形态：

```
telemetry_cache_push(rec)  →  xf_ring_push(XF_RING_TELEM, ...)
event_cache_push(rec)      →  xf_ring_push(XF_RING_EVENT, ...)
telemetry_cache_peek(&rec) →  xf_ring_peek(XF_RING_TELEM, ...)  // 读进 s_peek
event_cache_peek_at(i,...) →  xf_ring_peek_at(XF_RING_EVENT, i, ...)
*_reset()                  →  xf_ring_clear(...)
```

- 每个缓存模块只留一块**单条**返回缓冲（`s_peek`），不再有 `g_tc[128]` / `g_ev[256]`。
- **没有降级路径**：`xf_ring_push` 返回 false（坏块/擦除失败/空间不足）即这一条丢弃，
  `telemetry_cache_dropped()` / `event_cache_dropped()` 加一。Flash 不可用时同理。
- 上层 `app_backfill_poll` / `app_telemetry_backfill_poll` 调的是缓存模块接口，与规划一致。

> 唯一保留的"额外缓冲"是 `event_cache` 的**待提交槽**（`s_pend`，28 B）：
> NOR 不能就地改写，合并只能发生在"还没写进 Flash"的那一条上。详见 §4.3。

### 4.3 关键行为约定

| 项 | 约定（★= 实际实现值） |
|---|---|
| 什么时候写 Flash | **只在"发不出去"时**（离线 / publish 失败）。在线且发成功 → 根本不进队列，零 Flash 写 |
| 写失败 | **丢弃并计数**（`*_dropped()` 加一），不阻塞、不重试。Q3 之后没有 RAM 兜底 |
| 补报顺序 | 严格等于写入顺序（= 采集顺序），天然按 `ts` 单调 |
| 补报节流 | 保持 1 条/秒（`app_telemetry_backfill_poll`） |
| META 落盘 | ★ 统一节流：环指针变脏后**空闲 30 s** 才落一次（`XF_RING_FLUSH_IDLE_MS`）。掉电最多丢 1 条 head 记录，开机从旧 head 前向扫描补回（上限 64 条 / 一个扇区） |
| 恢复出厂 / 换绑 | ★ `sys.factory_reset` → `telemetry_cache_reset()` + `event_cache_reset()` → `xf_ring_clear()` |
| 记录格式 | 头部 `magic/len/seq/crc32`（12 B）+ 负载 ≤ 52 B，尺寸不符的记录丢弃并计数 |

> **★ 实施后必须知道的运行期影响：补报没排空时，实时遥测不发**
> `app_uplink.c` 里有一道既有门禁 `if (telemetry_cache_count() != 0) return;` —— 
> 队列非空就不发这一拍的 30 s 聚合遥测，先把欠的按 `ts` 顺序补完。
> 这是 **Q2"严格按 ts 递增"的必然结果**：想插队发新的，顺序就乱了。
>
> 以前队列最多 128 条、约 2 分钟排空，几乎感觉不到；现在容量涨到 49,152 条，
> 断网 1 天（4 台 × 300 s ≈ 1,150 条）补报约 19 分钟，断网 10 天约 3.2 小时。
> 这段时间平台看到的是**顺序正确但滞后**的数据 —— 数据不丢，只是晚到。
> 若将来无法接受，只能放弃"严格 ts 顺序"（例如给实时帧打 `live:true` 允许插队），
> 那是平台侧协议改动，不是固件单方面能定的。


### 4.4 容量对比（改完之后的账）

| 项 | 现在 | 改完 |
|---|---|---|
| 遥测可补报 | RAM 128 条 ≈ 4 台 × 300 s ≈ **2.7 小时** | Flash 49,152 条 ≈ **204 天** |
| 事件可补报 | RAM 256 条 ≈ 200 条/天 ≈ **1.3 天** | Flash 32,768 条 ≈ **164 天** |
| 缓存占 RAM | 11 KB | **≈ 64 B**（`s_peek` 32 B + `s_pend` 28 B；实测 ZI 少 11,064 B） |
| 掉电丢数据 | 最多 128/256 条 | **最多 1 条** |

### 4.5 磨损算账（改完之后）

- 写入速率 = 记录产生速率（只在断网/失败时）：4 台 × 300 s = 0.8 条/分。
- 4 KB 扇区装 64 条 ⇒ 每 80 分钟擦 1 次；TELEM 有 768 个扇区，同一扇区 **80 分钟 × 768 ≈ 42 天**才轮到一次。
- 连续断网一年：单扇区 ≈ 9 次擦除。W25Q64 单扇区 10 万次 ⇒ 余量充足。
- META 按 4.3 的节流（脏后空闲 30 s）：**纯连续断网**时 2,880 次/天 ≈ 105 万次/年。
  ★ **已扩到 16 槽轮转**（`XF_META_SLOTS`，META 区 64 KB 正好用完），单槽 ≈ 6.6 万次/年，
  W25Q64 单扇区 10 万次 ⇒ **最坏情况（一年 365 天全程断网）1.5 年磨完一轮**。
  注意这只是"一直在断网"的极端值；正常在线时队列不写、META 也不写，实际寿命远大于此。
  若将来觉得不够，把节流从 30 s 放宽到 300 s 即可 ×10（代价：掉电最多多丢几条 head 待补记录）。

## 5. 迁移步骤（每步可独立验证、可回退）

| 阶段 | 做什么 | 验收 | 状态 |
|---|---|---|---|
| **S1** | `xflash_store` 补上队列需要的原语：`xf_ring_count` / `peek_at` / `drop_n` / `clear`；META 16 槽轮转 + RAM 缓存；开机 head 前向扫描补回 | `test_xflash` 100 项通过 | ✅ |
| **S2** | `telemetry_cache` 切到"只写 Flash"，删 RAM 环与 `*_flash_recover` | `test_telemetry_cache` 37 项：顺序 / 落盘 / 淘汰 / 负水位 | ✅ |
| **S3** | `event_cache` 切到"只写 Flash"，合并改"待提交槽"；接入启动、主循环、恢复出厂、`#flash` | `test_event_cache` 65 项 + `test_cloud` 1140 项 | ✅ |

**行为变更（须知会平台/测试）**：事件合并窗口从"环里任意一条"收窄为"队尾那一条"。
原因：NOR 不能就地改写（要改写必须先擦 4 KB，会连带擦掉同扇区 63 条记录）。
实际影响很小 —— 每台设备每个上报周期只发一条，所以"每台每周期一条"的目标不变；
换来的是落盘顺序严格按 `ts` 递增。若中间夹了别的记录，同 key 的会新增一条而不是合并。

S1 不改任何业务行为（缓存仍走 RAM），风险最低；S2 才是行为变更，必须有 S1 的测试垫底。

## 6. 已拍板（2026-11-11）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 在线正常时，数据要不要也进 Flash（做"全量历史"）？ | **不要**：只有"发不出去"的记录才入队，在线成功不发的一次 Flash 都不写 |
| Q2 | 补报顺序必须严格按 `ts` 递增吗？ | **必须**：单写天然满足，实现与测试都按这条钉死 |
| Q3 | 没焊 Flash 的老板子还要不要继续支持？ | **不考虑**：开发阶段只有新板，删掉 RAM 后端；Flash 不可用时计入 `dropped` |
| Q4 | 事件和遥测要不要合成一个环？ | **不合并**：两者 topic、消费者都不同，后续 MQTT 主题还要改，分开更好排障 |

# 存储空间分配方案（内部 Flash / RAM / 外置 Flash）

> 2026-11-12 · 数据来源：`MDK-ARM/Listings/CDC.map`（同一天 -Oz 构建）+ 代码核实
> 配套：`docs/资源预算规划-20261112.md`（RAM/Flash 的量化账本）
> 所有"零引用"结论都由 `grep` 全工程调用点得出，不是看注释

---

## 0. 结论速览

1. **内部 Flash 其实很空**：512 KB 里代码只占 176 KB，剩下 **331 KB 空闲**，
   其中 208 KB 是 Slot B（只在升级时用）、**48 KB 是死区（零引用）**。
2. **外置 Flash 8 MB 里只有 6 MB 在干活**：CFG / OTA / FW_FACTORY / FACTORY / SPARE
   一共 1.9 MB **设计好了但一行调用都没有**。
3. **OTA 有一个会让升级"静默失效"的缺陷**（§6.2 D1），以及"最后保险"没接线（D3）。
   这两件比省空间更急。

## 1. 三块存储的家底

### 1.1 内部 Flash（512 KB，页 8 KB，擦写寿命约 1 万次）

| 区 | 地址 | 大小 | **实际占用** | 状态 |
|---|---|---:|---:|---|
| BootLoader | 0x08000000 | 16 KB | 3,136 B | ✅ 在用，余 12.9 KB |
| **Slot A（运行）** | 0x08004000 | 208 KB | 172,648 B | ✅ 在用，余 **39.4 KB** |
| **Slot B（OTA 暂存/回滚）** | 0x08038000 | 208 KB | 0（仅升级时写） | ✅ 在用，**208 KB 平时闲置** |
| OTA 标记/启动记录 | 0x0806C000 | 8 KB | 512 B 固定 + 240×32 B 启动记录 | ✅ 在用，**8 KB 已被排满** |
| 设备参数 | 0x0806E000 | 8 KB | 344 B | ✅ 在用，余 7.7 KB |
| 配置 A | 0x08070000 | 8 KB | 2,644 B | ✅ 在用 |
| 配置 B | 0x08072000 | 8 KB | 2,644 B | ✅ 在用（双备份） |
| **事件日志** | 0x08074000 | **48 KB** | **0** | ❌ **零引用死区** |
| 合计 | | 512 KB | ≈ 181 KB | 空闲 331 KB |

> `FM_HAS_EVENT_LOG=1` 还开着，但 `FM_EVENT_ADDR` 在全工程 `.c` 里**没有任何引用** ——
> 这块能力已经被外挂 Flash 的 EVENT 环取代了，属于遗留规划。

### 1.2 外置 Flash（W25Q64 8 MB，扇区 4 KB，擦写寿命 10 万次）

|---|---|---:|---|---|

| **OTA** | 0x620000 | 512 KB | OTA 整包暂存、可续传 | ❌ **只有单测引用** |
| **FW_FACTORY** | 0x6A0000 | 1 MB | 出厂固件镜像（最后保险） | ❌ **只有单测引用** |

| SPARE | 0x7B0000 | 320 KB | 预留 | — |

### 1.3 RAM

详见 `docs/资源预算规划-20261112.md`。结论：**165.9 KB / 192 KB（86.4%），余 26.1 KB**；
大头是 4G 42.7 KB、配置+云端暂存 39.3 KB、云端上下行 25.9 KB、cJSON 池 24 KB。
存储分配方案本身不增加 RAM，但 §6 的 OTA 差分会额外要 2~4 KB（已在预算内）。

## 3. 分配方案（这是本文的核心）

### 3.1 分配原则

| 判据 | 落到内部 Flash | 落到外置 Flash |
|---|---|---|
| 启动早期就要用（SPI 可能还没起来） | ✔ | ✘ |
| BootLoader 必须直接读 | ✔ | ✘ |
| 体积 < 8 KB 且写得不频繁 | ✔ | ✘ |
| 体积大 / 高频写 / 可重建 / 历史归档 | ✘ | ✔ |
| 抢救路径（最后保险）要用 | 主副本 ✔ | **备份 ✔** |

### 3.2 内部 Flash 保留（不做任何迁移）

| 保留项 | 大小 | 为什么必须留在内部 |
|---|---:|---|
| BL + Slot A + Slot B | 432 KB | 代码本体；A/B 是回滚能力的物理基础 |
| OTA 标记 / 启动记录 | 8 KB | **BL 的最短读取路径**，放外置就要给 BL 加 SPI 驱动（增加救命路径的依赖面） |
| `device_param_t` | 344 B | 4G 上线、LoRa 建链之前就要用；此时外置 Flash 刚初始化完，不能当唯一来源 |
| 配置 A/B 双备份 | 2×2,644 B | 启动第 2 秒就要读；双 bank + CRC32 已经足够；体积极小 |

**明确不建议改的一条**：不要为了省 5 KB 把配置搬去外置 Flash。
配置是"设备身份的延伸"，一旦 SPI Flash 坏块/接触不良，设备会以出厂默认身份上线，
在平台上表现为"一台新设备"，比"起不来"更难排查。

### 3.3 外置 Flash 该承接什么

| 承接项 | 用哪个区 | 大小 | 现状 | 动作 |
|---|---|---:|---|---|
| 事件/遥测/日志三环 | EVENT/TELEM/LOG | 6 MB | 已在跑 | 不动 |
| **出厂固件镜像** | FW_FACTORY | 512 KB | 空转 | **接线**（§6 O4） |
| **配置历史快照** | CFG | 64 KB | 空转 | **启用**：每次 `cfg.set` 通过后追加一份，支持"回滚到上一版配置" |
| **出厂参数备份** | FACTORY | 64 KB | 空转 | **启用**：产线写一份，`sys.factory_reset` 时用于交叉校验 |
| **OTA 整包/差分包暂存** | OTA | 512 KB | 空转 | **启用**（§6 O2/O3） |
| **崩溃黑匣子** | 新增 DIAG | 64 KB | 无 | 新建（配合内部 §4 的 dump） |

### 3.4 一句话回答"哪些配置放哪"

> **"启动必需的、小到几百字节的" 留内部；"可归档、可重建、会不断追加的" 放外置。**
> 具体就是：`device_param_t` + 配置 A/B + OTA 标记 → 内部；
> 配置**历史**、出厂**备份**、出厂**固件**、OTA **暂存** → 外置。

## 4. 内部那 48 KB 死区怎么处理

两个方案，取决于是否愿意重排分区（会牵动已部署设备）。

| | 方案 A：零迁移（推荐先做） | 方案 B：重排分区（新批次再做） |
|---|---|---|
| 做法 | 0x08074000 起 48 KB 拆成：崩溃黑匣子 16 KB + 预留 32 KB | 删掉 EVENT 区，**Slot A 208 → 256 KB** |
| 新布局 | 地址全不变 | BL 16 + A 256 + B 208 + META 8 + PARAM 8 + CFG 16 = 512 KB |
| 收益 | 多一个掉电不丢的崩溃现场；地址零风险 | App 余量 **39.4 → 87.4 KB**，直接解决"固件到头" |
| 代价 | 40 KB 继续闲置 | 所有设备重烧 BL+App；CFG/PARAM/META 地址全变 → **现场配置全丢，要重新下发** |
| 适用 | 现在就能做 | 量产前的最后一次布局定稿 |

> 我的建议：**先按方案 A 把死区用起来（半天工作量），把方案 B 留到"确认还有第二个大功能要上"时一次性做**。
> 现在 Slot A 还剩 39.4 KB，配合 §O3 的差分升级和日志裁剪，够撑一轮迭代。

## 5. 外置 Flash 重新分区建议（零迁移）

好消息：**要动的区全是当前零引用的区，EVENT/TELEM/LOG 的基址一个字节都不用改，
所以不需要任何数据迁移。**

| 区 | 现在 | 建议 | 变化 | 理由 |
|---|---|---|---:|---|
| META | 64 KB | 64 KB | — | 16 槽轮转已够 |
| CFG | 64 KB | 64 KB | — | 16 份配置历史，够回溯 |
| EVENT | 2 MB | 2 MB | — | 约 3.2 万条，不动 |
| TELEM | 3 MB | 3 MB | — | 约 4.9 万条，不动 |
| LOG | 1 MB | 1 MB | — | 不动 |
| OTA | 512 KB | 512 KB | — | 整包 168 KB + 差分包，2.5 倍余量 |
| FW_FACTORY | 1 MB | **512 KB** | −512 KB | 镜像只有 168 KB，1 MB 是浪费 |
| FACTORY | 64 KB | 64 KB | — | |
| **DIAG（新增）** | — | **64 KB** | +64 KB | 崩溃黑匣子 + 掉电诊断包 |
| SPARE | 320 KB | **768 KB** | +448 KB | 吸收 FW_FACTORY 让出的空间 |

基址（全部 64 KB 对齐，正好排满 8 MB）：

```
META       0x000000   64 KB
CFG        0x010000   64 KB
EVENT      0x020000    2 MB
TELEM      0x220000    3 MB
LOG        0x520000    1 MB
OTA        0x620000  512 KB
FW_FACTORY 0x6A0000  512 KB   ← 原来 1 MB
FACTORY    0x720000   64 KB   ← 地址变了（原 0x7A0000），但从未被写过
DIAG       0x730000   64 KB   ← 新
SPARE      0x740000  768 KB
           0x800000  = 8 MB ✓
```

> ⚠️ 改动点只有两处：`app/drivers/xflash/xflash_store.c:17` 的 `s_regions[]` 数组
> 和 `xflash_store.h` 的区域枚举（加 `XF_REGION_DIAG`）。
> `META` 里存的是各环的**相对偏移**（`ring_head[]` 注释明确"相对环起点"），
> 所以**不需要格式化、不会丢三环数据**。上线前用 `#flash info` 核对一次即可。

## 6. OTA 升级优化

### 6.1 现在的流程

```
云端 ota.start(url, md5, size)
   └─ cloud_cmd_ota.c:105  目标槽 = 当前槽 ^ 1
   └─ ota_port_set_stage(目标槽地址)
HTTP 分片下载 ──→ 直接写入【目标槽】（内部 Flash）
   └─ 边下边写；续传记录写在 META 页
校验通过 ──→ ota_port_mark_valid()：擦 META 整页 + 写 32 B 标记
重启 ──→ BL：校验 CRC → 擦【Slot A】→ 从【Slot B】逐 8 B 复制到 A → 跳 A
```

### 6.2 三个已确认的缺陷

#### D1（严重）搬运方向写死 B→A，与"目标槽取反"矛盾 → 升级静默失效

证据链：

| 位置 | 内容 |
|---|---|
| `cloud_cmd_ota.c:105` | `tgt = ota_port_current_slot() ^ 1` —— 目标是"当前槽的反面" |
| `ota_port.h:190-200` | 标记只有 32 B：`magic / crc32 / size`，**没有槽号字段** |
| `bootloader.h:34` | `BL_APP_ADDR = FM_SLOT_A_ADDR` —— 目标写死 A |
| `bootloader.h:36` | `BL_OTA_BUFFER_ADDR = FM_STAGE_ADDR = FM_SLOT_B_ADDR` —— 源写死 B |
| `bootloader.c:187` | `bl_copy_to_app()` 只做 B → A |

推演：设备因 A 槽向量表损坏而跑在 B 槽 → 云端下发升级 → **新固件被写进 A** →
重启后 BL 擦掉 A、把 **B（旧固件）复制到 A**、跳 A。
**结果：新固件被丢弃，设备回到旧版本，而云端只看到"下发成功"。**

修法（半天）：
- 正解：`ota_mark_t` 的 `reserved[12..31]` 里放 `src_slot` / `dst_slot` 各 1 B，
  BL 按字段选源和目标（同时把 `bl_erase_app_area` / `bl_copy_to_app` 参数化）。
- 兜底（更快）：`cloud_cmd_ota.c` 在 `current_slot()==1` 时直接拒绝升级并上报原因。

#### D2（中）标记页一次升级被整页擦 2 次，顺手清掉续传与健康记录

`mark_valid()` / `mark_invalid()` 都是"擦整页 8 KB"，而这一页里还住着
HTTP 续传记录（80 B）和 240 条 A/B 启动记录。代码注释里也承认 `try_count` 会归零。
后果：下载中断后续传位图丢失、健康计数被重置。属于"已接受的设计"，但可以顺手改好（见 O5）。

#### D3（中）"最后保险"是空的

`FW_FACTORY`（1 MB）+ `xf_fw_factory_*` 五个接口全部写好，
但**全工程只有 `test_xflash.c` 调用**；`#flash` 里没有 `fwif` 子命令；
`sys.factory_reset` 也不走它。**A/B 双槽都坏时没有任何兜底。**

### 6.3 优化项

| 编号 | 内容 | 收益 | 成本 | 优先级 |
|---|---|---|---|---|
| **O1** | 修 D1：标记加槽号 + BL 双向搬运 | 消除"静默升级失败" | 0.5 天 | **P0** |
| **O2** | FW_FACTORY 接线：`#flash fwif write/verify` + 恢复出厂兜底 | 真有最后保险 | 1 天 | **P0** |
| **O3** | **页级差分升级**：只下发变化页 + 页位图，未变页由 **App 从 Slot A 本地读出来**写进暂存区 | 空中流量 **−40%~−76%**；不改 BL、不改链接 | 云端工具 + App 位图逻辑，1~1.5 天 | **P1** |
| **O4** | 下载落**外置** OTA 区，校验通过后再由 BL 写内部 | 内部 Flash 每次升级少擦 26 页；断电只丢暂存 | BL 加 SPI 读 ~2 KB（BL 余 12.9 KB） | P1 |
| **O5** | 续传记录 / 健康记录挪出标记页（外置 DIAG 或 META 第二页） | 不再被整页擦连带清掉 | 0.5 天 | P2 |
| **O6** | LZ4 流式压缩传输 | 168 KB → 约 105 KB；与 O3 叠加可到 20~30 KB | App +1.5 KB 代码 + 4~8 KB RAM | P2 |

**关于 O3 的细节（这条性价比最高，值得展开）**

- 镜像 172,648 B ≈ **21 个 8 KB 页**。相邻两版通常只改 4~12 页。
- 包结构：`页位图(21 bit) + 每页 CRC32 + 变化页数据`。
- App 侧：写暂存区时，位图=0 的页直接从 **当前运行的 Slot A** 读出来写进去
  （App 跑在 A，读 A 是安全的；目标槽是 B，写 B 也安全）。
- **完全不改 BootLoader、不改链接地址**，这是它比 O4 更适合先做的原因。
- 前提：镜像按页对齐、构建可复现（同工具链同优化等级 —— 目前 `-Oz` 已固定）。
- 兜底：云端判断变化页超过 60% 时，直接发全量包，设备侧逻辑不变。

**关于"为什么不把 OTA 改成真正的 A/B swap"**

真正的 swap 要求 B 槽里的镜像能就地运行，但 Cortex-M 的代码是绝对地址链接的
（整个固件链接在 0x08004000），搬到 0x08038000 就跑不起来。
所以现在"下载到 B、再拷到 A"是**为了规避重定位**的必然设计，不是偷懒。
要做真 swap，得让云端为两个槽分别出包（两份链接地址不同的镜像），复杂度和产线风险都翻倍，
**不建议在当前阶段做**。

### 6.4 推荐路线

```
第一步（本周）  O1 修 D1  +  O2 接 FW_FACTORY        ← 正确性与兜底，不改架构
第二步（下周）  §4 方案A 用掉 48 KB 死区 + §5 外置重新分区（零迁移）
第三步（功能前）O3 页级差分                            ← 省流量，为现场升级铺路
第四步（可选）  O4 / O5 / O6
```

## 7. 落地顺序与验收

| 步骤 | 动作 | 验收方法 |
|---|---|---|
| 1 | O1：标记加槽号，BL 双向搬运 | 手工把 A 槽向量表擦坏 → 跑 B → 云端升级 → 确认落到 B 版本 |
| 2 | O2：FW_FACTORY 接线 | `#flash fwif write` → 擦 A/B → 重启 → 能从外置恢复 |
| 3 | §4 方案 A：48 KB 死区做黑匣子 | 人为 HardFault → 重启 → `#flash dump` 读得到现场 |
| 4 | §5 外置分区调整 | `#flash info` 核对新区表；三环数据条数不变 |
| 5 | O3：页级差分 | 同一份 bin 发全量 vs 差分，比对实际下载字节数 |

答复对象：内部 Flash 新分区、外挂 Flash 新分区、档位 4→7、topic 扩到 10+ 的资源可行性。
所有数字取自 `CDC.map`（11-12 10:12 那次 -Oz 构建，ROM 172,648 B / RAM 169,920 B）与源码实测。

## 一、内部 Flash 512 KB —— 你的方案 + 补齐两个漏项

你给的口径是：BL 16 KB、App-A 224 KB、App-B 224 KB、删事件日志、配置 A/B 共 32 KB。
**这四个加起来是 496 KB，还剩 16 KB。** 而 `META`（OTA 标记 + 240 条启动记录）和 `PARAM`（设备参数，344 B）是必须存在的，各占 1 页 8 KB —— **刚好补满 512 KB**。

| 区 | 起始 | 大小 | 页数 | 说明 |
|---|---|---:|---:|---|
| BootLoader | `0x08000000` | 16 KB | 2 | 不变，实际 3,136 B |
| **App-A（运行槽）** | `0x08004000` | **224 KB** | 28 | ← 208 → 224，**+16 KB** |
| **App-B（OTA/回滚槽）** | `0x0803C000` | **224 KB** | 28 | ← 208 → 224，**+16 KB** |
| META | `0x08074000` | 8 KB | 1 | OTA 标记 [0..511] + 启动记录 [512..] |
| PARAM | `0x08076000` | 8 KB | 1 | 设备参数 344 B |
| **CFG-A** | `0x08078000` | **16 KB** | 2 | ← 8 → 16 |
| **CFG-B** | `0x0807C000` | **16 KB** | 2 | ← 8 → 16 |
| **合计** | | **512 KB** | **64** | 正好排满，零浪费 |

事件日志 48 KB 已彻底消失（删除后 A/B 各吃 16 KB，META/PARAM 各吃 8 KB）。

### 1.1 App 区余量

| | 现在（208 KB） | 改后（224 KB） |
|---|---:|---:|
| 容量 | 212,992 B | 229,376 B |
| 固件 | 172,648 B | 172,648 B |
| **余量** | **39.4 KB（18.5%）** | **55.4 KB（24.2%）** |

后面档位扩到 8、topic 扩到 12 两项加起来大约 +1.6~2.6 KB（见第三节），**做完还有 52 KB 以上**。

### 1.2 但 CFG 的 16 KB 里有一半现在用不上

单页 8,192 B，减去头部（magic/seq/crc/len 约 28 B）**JSON 上限约 8,150 B**。

- 4 档配置 JSON 实测约 **2,000 B**（`cfg_t` 结构体是 2,644 B，JSON 更紧凑）
- 8 档后约 **3,100 B**（每档 JSON 约 260 B × 4 = +1,040）
- **3,100 << 8,150，一页就装下了**

所以每个 bank 给 16 KB，**第 2 页是空的**，除非改 `cfg_bank_write()` 支持跨页（擦 2 页 / 写 2 页 / CRC 跨页校验，约 200 行，动的是配置存储核心）。

**我的建议：分区就按 16 KB 定，地址不要变**。理由：
1. 分区地址定死比省 16 KB 值钱得多——改地址要**重编并重烧 BL**（`BL_APP_MAX_SIZE` 写死在 BL 里），现场设备靠 App OTA 永远改不到 BL；
2. 省下的 16 KB 也没地方可用（PARAM 只用 344 B，META 够用）；
3. 将来配置真涨过 8 KB 时，只要改 `cfg_bank_write` 的跨页逻辑，**分区地址不用动**。

> 一句话：把这 16 KB 当"预埋的扩容余量"，现在不接。

## 二、外挂 Flash 8 MB —— 按评估方案落地

| 区 | 起始 | 大小 | 用途 | 状态 |
|---|---|---|---:|---|
| META | `0x000000` | 64 KB | 超级块 16 槽轮转 + 坏块位图 | ✅ 在用 |
| CFG | `0x010000` | 64 KB | **产线配置基线**（可存 20+ 套模板） | 待接 |
| EVENT | `0x020000` | 2 MB | 事件补报队列（64 B 槽 × 32,672） | ✅ 在用 |
| TELEM | `0x220000` | 3 MB | 液位遥测队列 | ✅ 在用 |
| FW_FACTORY | `0x520000` | 512 KB | 出厂固件镜像（救砖 / 回出厂） | 待接 |
| ROLLBACK | `0x5A0000` | 1 MB | 最近 4 个健康版本（要 N-2 回滚才用） | 新增 |
| FACTORY | `0x6A0000` | 64 KB | 产线数据（序列号 / 校准值） | 待定 |
| DIAG | `0x6B0000` | 64 KB | 崩溃现场（HardFault 寄存器 + 栈回溯） | 新增 |
| SPARE | `0x6C0000` | 1.25 MB | 预留 | — |

**LOG 1 MB 已删除**。EVENT / TELEM 基址不变（`0x020000` / `0x220000`），META 存的是相对偏移，**所以只需改 `xflash_store.c` 的分区数组，不需要格式化**。

> ⚠️ 但 `xf_meta_t` 的 `ring_head/tail/dropped[3]` 要改成 `[2]`，这是**改结构布局** →
> `XF_META_VERSION` 必须 1→2，版本不匹配时直接 `xf_ring_format_all()` 清空三环。
> 开发阶段没有存量设备，这条只是防止自己踩坑。

**ROLLBACK 1 MB 是否必要**：如果你接受的回滚深度是"只管上一版"，1 MB 可以省掉（上一版本就在另一个 Slot 里）。要"回滚到 N-2/N-3"或"保留出厂版 + 上一版两份"才需要它。**建议保留**，反正 SPARE 有 1.25 MB 也没别的用途。

## 三、档位 4 → 7（或 8）的影响

先确认口径：你说"档位加到 7 个"。现有 `CFG_GEAR_COUNT = 4`（gear **0~3**）。加到 7 个有两种读法：

| 读法 | 宏值 | gear 编号 | 说明 |
|---|---|---|---|
| **甲** | `CFG_GEAR_COUNT 7` | 0~6 | "共 7 个档位" |
| **乙** | `CFG_GEAR_COUNT 8` | 0~7 | "扩充到第 7 号"（现有注释写的就是 `4~7 需先解决预算`） |

`config_store.h:117` 的原注释是 `gears[] 0~3; 4~7 需先解决 RAM/JSON/cJSON 池预算` —— 说明当初的设计意图是**乙（0~7，共 8 个）**。下面按 **8 个** 算，按 7 个算的话所有增量再乘 0.75。

### 3.1 单档结构体实测

`cfg_gear_t` 手工布局核算 = **365 B，4 字节对齐后 368 B**：

| 字段 | 字节 |
|---|---:|
| gear / targets_all / target_count / sound_mode / voice / led_show_mode / led_text_show_mode[2] / led_color[2] | 10 |
| `target_uid[5][27]` | 135 |
| `name[33]` | 33 |
| `led_text1[49]` + `led_text2[49]` | 98 |
| `tts_text[89]` | 89 |
| **合计（含 3 B 尾部填充）** | **368** |

### 3.2 各项增量

| 项 | 现在（4 档） | 8 档 | 增量 |
|---|---:|---:|---:|
| `sizeof(config_store_t)` | 2,644 B | **4,104 B** | **+1,460 B** |
| 配置 JSON 文本 | ~2,000 B | ~3,100 B | +1,040 B |
| cJSON 池最坏占用 | 14,632 B | ~18,500 B | +3,900 B |
| `config_store_factory_default()` 代码 | — | — | +0.4 KB (Flash) |
| **RAM：5 份 cfg_t 副本** | 13,220 B | **20,520 B** | **+7,300 B** ⚠️ |
| **RAM：合并成 2 份** | 13,220 B | **8,208 B** | **−5,012 B** ✅ |

**关键判断：cJSON 池 24 KB 够不够？**
最坏 14,632 → 约 18,500 B（增幅按档位比例 1.26×），**24 KB 仍有余量 5.5 KB**，不用扩。但已经不算宽裕 —— 如果将来 sensor/device 也各扩几个，就要重新算。

**关键判断：CFG_JSON_MAX 6,144 够不够？**
8 档 JSON 约 3,100 B，**够，且余 3 KB**。`config_store.c:97` 那条 `sizeof(config_store_t) <= CFG_JSON_MAX` 的编译期断言，8 档后是 4,104 ≤ 6,144，也能过。**不用改。**

⚠️ 但这条断言本身是错的——它比的是**结构体**大小，不是**JSON 文本**大小。JSON 通常比结构体小（省了定长数组的空白），所以断言偏保守、不会误放行。**不用改，但要知道它不是真正的保护。**

### 3.3 档位扩展的代码改动面

`CFG_GEAR_COUNT` 全工程 **17 处引用**，全部是循环上界或范围校验，**改宏值即可，无需改逻辑**：

| 位置 | 用途 |
|---|---|
| `config_store.h:392` | `cfg_gear_t gears[CFG_GEAR_COUNT]` |
| `config_store.c:416 / 639 / 1276` | 默认值循环 / 校验循环 / dump 循环 |
| `config_parse.c:519` | `cnt > CFG_GEAR_COUNT` 范围校验 |
| `config_serialize.c:128` | JSON 序列化循环 |
| `level_eval.c:563` / `level_supervisor.c:261` | 档位越界保护 |
| `lora_alarm.c:383` | 0x03 载荷档位合法性 |
| `app_level.c:122/127` | 强制档位越界夹取 |
| `cloud_cmd_devices.c:915` / `app_console.c:424/845/856/859` | 参数校验与打印 |

**真正需要动的只有一处**：`config_store.c:416` 的默认值循环 —— 现在写的是 `for (gi = 4u; ...)` 生成"预留N"档，8 档后自动生成 4 个预留档，逻辑天然正确。

**结论：档位 4→8 的代码改动极小（< 50 行），成本几乎全在 RAM 上。**

### 3.4 有一个必须确认的业务问题

`level_eval` 的阈值判定只认 4 个状态：`CFG_GEAR_RESOLVED(0) / NORMAL(1) / WARNING(2) / ALARM(3)`（`config_store.h:235-238`）。

**8 个档位里，4~7 号档的语义是什么？**
- 如果只是"手动可选档"（现有默认就是 `sound_mode=0`、无文本，等云端配），那**代码一行不用改**，只是多了 4 个可配置槽；
- 如果 4~7 要参与**自动状态判定**（比如"重度告警""断电""检修"），那 `level_eval` 的判定逻辑要重写，`thresholds` 也要从 3 个阈值扩到 7 个，**这是另一个量级的改动（约 300 行 + 阈值配置模型变更）**。

**这个必须先定，否则预算算不准。** 下面按"仅扩展可配置槽"估算。

## 四、topic 5 → 10+ 的影响

现有抽象层很干净：`cloud_topic_t` 枚举 + `cloud_profile_topic_name/qos/retained` 三个访问器 + 一张表。

当前 5 个：

| 枚举 | 主题 | 方向 |
|---|---|---|
| `CLOUD_TOPIC_CMD` | `rt/gw/{gwId}/cmd` | 下行 |
| `CLOUD_TOPIC_CMDRESP` | `rt/gw/{gwId}/cmdresp` | 上行 |
| `CLOUD_TOPIC_TELEMETRY` | `rt/gw/{gwId}/telemetry` | 上行 |
| `CLOUD_TOPIC_EVENT` | `rt/gw/{gwId}/event` | 上行 |
| `CLOUD_TOPIC_LWT` | `rt/gw/{gwId}/lwt` | 遗嘱 |

### 4.1 资源影响（很小）

| 项 | 现在 | 12 个 topic | 增量 |
|---|---|---|---|
| 后缀字符串（rodata） | ~60 B | ~160 B | **+100 B Flash** |
| 订阅遍历 + URC 分流代码 | — | — | **+0.5~0.8 KB Flash** |
| 常驻完整 topic 缓冲 | `g_sub_topic[96]` + `g_pub_topic[48]` + `g_lwt_topic[80]` = 224 B | 12 × 48 = 576 B（表） | **+352 B RAM** |

**topic 增加几乎不耗资源**，因为主题名是"gwId + 后缀"运行时拼的，`gwId` 是 26 位 hex 共用一个。

### 4.2 真正的工作量在别处

| 项 | 说明 | 约 |
|---|---|---|
| 多 topic 订阅 | 现在只 SUB 一个 `cmd`；12 个要逐条 `AT+MQTTSUB`，且要在 ONLINE 后按序下发、失败重试 | 150 行 |

| QoS / retained 差异化 | 每个 topic 独立的 QoS 和 retained 标志，表里已支持 | 0（改表即可） |
| topic 上限保护 | `G4_SUB_TOPIC_MAX 96` 要覆盖最长的 topic；`g_pub_topic[48]` 要够（`rt/gw/26hex/` = 34 B + 后缀） | 0~50 行 |

**结论：topic 从 5 到 12，Flash +0.9 KB、RAM +0.35 KB，工作量 1~1.5 天。**

## 六、改分区必须先知道的三件事

### 6.1 BootLoader 必须重编并重烧

`bootloader.h` 里写死了：
- `BL_APP_ADDR` = Slot A 起始
- `BL_OTA_BUFFER_ADDR` = Slot B 起始
- `BL_APP_MAX_SIZE` = 208 KB ← **改成 224 KB 必须改这个**

**App 大小一变，BL 就必须重烧**。而现场设备只能靠 App OTA 升级，**永远改不到 BL**。所以：
- 开发阶段（现在）：随便改，重烧一次即可；
- **量产之后：Slot 大小绝对不能变**，再改就是返厂。

这条要在动手前写进文档，避免将来手滑。

### 6.2 要改的地址常量清单

| 文件 | 内容 |
|---|---|
| `app/common/flash_map.h` | 模式 2 的全部 `#define` + 8 条静态断言全部重写 |
| `bootloader/bootloader.h` | `BL_APP_ADDR` / `BL_OTA_BUFFER_ADDR` / `BL_APP_MAX_SIZE` |
| `MDK-ARM/CDC.uvprojx` | Target 的 IROM1 Size：`0x34000` → `0x38000` |
| `MDK-ARM/Objects/CDC.sct` | 若用手写 scatter（当前是 IDE 自动生成，改 uvprojx 即可） |
| `tools/flash_bl_app.ps1` | 烧录地址 `0x08004000` 不变，但长度校验要改 |
| `_host_test/test_flash_map*.c` | 断言全要跟着改 |

### 6.3 一条自检

改完先跑 `tools/res_report.py`，确认 ROM 数字变了但 RAM 没意外暴涨；再跑 `_host_test/run.ps1` 全绿；最后查 `CDC.map` 里 `ER_IROM1` 的起始是否还是 `0x08004000`。

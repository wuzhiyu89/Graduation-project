## 一、音色（已实现）

每个档位可单独指定播报音色，共 6 种。**云端沿用贵方现有的音色编号下发即可**，网关负责换算成声光设备的编号：

| 云端下发 | 音色 | 网关转给设备的编号 |
|---|---|---|
| 3 | 艾佳女声（**默认**） | 0 |
| 51 | 艾诚男声 | 1 |
| 52 | 艾达男声 | 2 |
| 53 | 艾琪女声 | 3 |
| 54 | 唐老鸭效果器 | 4 |
| 55 | 艾彤女童声 | 5 |

> 51~55 与 1~5 是一一对应的，只有"艾佳"两边不同（云端 3、设备 0）。换算已做在网关里，**贵方按下表左列下发、按左列显示即可，不需要自己换算**。

**云端需要做的**（在现有 `rule.set` / `rule.query` 的 `data.gears[]` 里增加 `voice` 字段）：

```json
{"cmd":"rule.set","msgId":"x1","ts":1700000000,
 "data":{"gears":[{"gear":1,"voice":53},{"gear":2,"voice":54}]}}
```

| 项 | 约定 |
|---|---|
| 取值 | 3 / 51 / 52 / 53 / 54 / 55，其它值回 `1001` |
| 兼容 | 0 / 1 / 2 / 4 / 5 也收（两套编号这几个值同义）；`3` 一律按"艾佳"，要"艾琪"请用 53 |
| 缺省 | 不填即为艾佳女声（等价于下发 `3`）；整份配置里没有 `voice` 字段的档位都按艾佳处理 |
| 查询 | `rule.query` 回读的 `voice` 是**云端编号**（51 ~ 55）；艾佳(3) 沿用既有格式省略不写，读到"没有 voice"即视为 3 |
| 持久化 | 写入网关配置区，掉电不丢、重启保持 |

> 说明：网关已把音色真正下发到声光设备，云端改完即生效，无需额外操作。

**手动播报也支持音色**：`dev.ctrl` 里同样可以带 `voice`（同一套码 3 / 51~55），例如

```json
{"cmd":"dev.ctrl","msgId":"d1","ts":1700000000,
 "data":{"uid":"all","gear":3,"voice":54,"ttsText":"你好，音色54"}}
```

这一条只影响**本次播报**，不会改动档位配置里保存的音色；不带 `voice` 就用该档位配置的音色。
（`voice` 取值非法时返回 `1001`，不会静默按默认音色播报。）

## 二、本地缓存（已实现）

| 缓存 | 对外承诺容量 | 内容 |
|---|---|---|
| **事件缓存** | **≥5000 条** | 状态迁移、联动下发、设备上下线、低电压等 |
| **遥测缓存** | **≥5000 条** | 逐台传感器每次上报（液位/电量/信号/原始时间戳） |

> 5000 条为对外保守承诺值，实际容量更大，为长期运行留足余量。

**相比上一版的关键改进：掉电不丢。** 上一版缓存在内存里，网关一断电（现场断电、
雷击跳闸、维护断电）历史全部清零；本版掉电重启后仍能继续补报。

**平台侧需知悉的补报行为：**

- 断网期间照常本地评估与联动，事件与遥测写入本地缓存；
- 恢复连接后按 **原始 `ts`** 逐条补报，遥测约 **1 条/秒**；
- 补报未排空时暂不发送实时遥测，保证平台看到的时间序列**严格单调**。
  断网 1 天补报约 19 分钟，4 天约 80 分钟——**数据不丢，只是晚到**；
- 请平台按 `ts` 入库与去重（补报 `msgId` 由 `(uid, ts, 序号)` 确定性生成，可安全去重）；
- 恢复出厂 / 重新绑定会清空缓存，避免把上一位用户的历史补报给新账号。

**能存多久**（按 5000 条承诺）：

| 场景 | 遥测覆盖 | 事件覆盖 |
|---|---|---|
| 4 台 × 300 s（出厂默认） | 约 4.3 天 | 约 25 天 |
| 4 台 × 60 s | 约 0.9 天 | 约 25 天 |

## 四、整机月流量

### 计算前提

| 参数 | 取值 |
|---|---|
| 上报周期 | 30 s（出厂默认） |
| 每次周期发 | 1 条 `status.report` + 1 条 `telemetry.report` |
| 传感器数量 | **4 台**（产品上限，按满配算） |
| 计费口径 | 含 MQTT 与 TCP/IP 报头，上下行均计 |

### 单包与月度明细

| 报文 | 单包（含协议开销） |
|---|---|
| `status.report` | 396 B |
| `telemetry.report`（4 台） | 677 B |

| 项 | 月流量 | 占比 |
|---|---|---|
| 周期上报 | 88.41 MB | 94.4% |
| MQTT 保活 | 3.46 MB | 3.7% |
| PUBACK 确认 | 0.66 MB | 0.7% |
| 事件上报（按 100 条/天） | 0.82 MB | 0.9% |
| 云命令与应答（按 20 次/天） | 0.29 MB | 0.3% |
| **合计** | **93.64 MB/月** | 100% |

### 结论

```
估算值        93.6 MB/月
× 1.5         140.5 MB/月
建议按        150 MB/月 部署
```

> **建议流量卡：200 MB/月 或 1 GB/年**（再留 OTA 与异常重连余量）。
> OTA 一次约 0.2 MB，一年 10 次仅 2 MB，可忽略。

### 如需进一步省流量

| 措施 | 效果 | 代价 |
|---|---|---|
| 上报周期 30 s → **60 s** | 流量**减半**（约 47 MB/月） | 平台刷新变慢一倍 |
| `status` 与 `telemetry` 合并 | 再省约 50%（约 40 MB/月） | 需改报文定义，双方都要动 |

周期改 60 s **只需改配置、不用改固件**，若对流量成本敏感可优先考虑。
